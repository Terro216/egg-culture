# Резервные копии пользовательских данных Egg Culture

## Состав

| Источник в `kladka_data` | Сохраняется |
| --- | --- |
| `egg-road/records.sqlite` | Вся БД: аккаунты, хеши паролей и кодов восстановления, сеансы, профили, Инициация, достижения, рекорды, прогресс игр и инкубатора; новые таблицы также входят автоматически |
| `posts.json` | Все записи: `pending`, `approved`, `rejected`; текст, аудитория, модерация и состояние доставки |
| `images/<id>.<ext>` | Все фотографии, на которые ссылается зафиксированный `posts.json`, включая закрытые и отклонённые записи |

По решению владельца **не входят сертификаты**: ни генерируемые именные PNG,
ни `private/fonin-gifts/`. Данные Инициации в аккаунте входят в БД: исключение
PNG не лишает пользователя статуса адепта. Также исключены новости, сборки,
логи, `.env`, исходники, временные файлы и изображения без записи в Книге.
Каталог проекта и сертификаты вообще не монтируются в backup-контейнер.

Гостевой `localStorage`, незавершённые игры и прочие данные, оставшиеся только
в браузере, сервер не получает и восстановить этим бэкапом не может.
Для восстановления всего сервера отдельно нужны Git/образ приложения,
его `.env`, rclone-конфигурация и ключ Restic. Аккаунты используют собственные
scrypt-соли и хеши внутри SQLite; отдельного внешнего ключа для входа нет.

Read-only проверка production 04.10: стандартные пути `/app/.kladka` и
`/app/.kladka/egg-road`, 17 таблиц, 2 аккаунта, 6 записей и 6 фотографий;
`quick_check=ok`, отсутствующих фотографий нет. Объём БД — 262144 байта,
связанных фотографий — 13289445 байт. Счётчики подтвердились в первом снимке
и при его восстановлении.
При изменении `KLADKA_DATA_DIR`, `EGG_ROAD_DATA_DIR` или Compose project name
нужно пересмотреть mount источника; нельзя продолжать копировать старый том.

## Проверка и восстановление

```bash
scripts/restore.sh validate <snapshot-id>  # временный каталог, удаляется после проверки
scripts/restore.sh drill latest           # та же полная проверка данных без запуска сайта
scripts/restore.sh export <snapshot-id>   # проверенная копия остаётся в staging
```

`latest` сначала разрешается в точный ID с нужными host/tag/path. `restic restore
--verify` восстанавливает его отдельно; ни один restore-режим не записывает
в `kladka_data`. `export` оставляет данные в
`/srv/egg-culture-backup/exports/<полный-ID>` и отказывается перезаписывать
существующий экспорт. После использования этот приватный каталог нужно удалить.
Drill проверяет БД, хеши и связность данных, но **не запускает HTTP-приложение**
и не проверяет вход реальным пользовательским паролем.

При согласованном восстановлении production:

1. Восстановить и проверить конкретный ID через `export`. Сохранить аварийную
   копию текущего тома, если он доступен, и запомнить image ID приложения.
2. Остановить только `web`, чтобы прекратились записи БД и модерация.
3. Взять из экспорта `egg-road/records.sqlite`, `posts.json`, `images/`.
   Предпочтительно заполнить новый том и сохранить старый для отката. Не
   накладывать SQLite на старые `-journal`, `-wal`, `-shm`. Сохранить UID/GID
   рабочего контейнера и приватные права; `manifest.json` не является
   пользовательскими данными приложения.
4. Подключить проверенный том и запустить совместимый образ. Убедиться в
   целостности, счётчиках, входе владельца, прогрессе, аудитории и фотографиях.
   Утверждать, что восстановление выполнено, только после проверки приложения.

Восстановление старой точки возвращает старые пароли/коды и сеансы. Сеансы
можно отозвать отдельным согласованным шагом; пароль/код, изменённые после
снимка, не появятся в прошлом снимке. Pending-доставки в Telegram после старого
restore могут повториться: действующий контракт приложения — at least once.

## Проверки разработки

`python3 -m unittest discover -s tests -p test_backup.py -v` использует DDL из
приложения и вымышленные данные: roundtrip всех таблиц и статусов, параллельные
SQLite-транзакции, изменение Книги во время копирования, потерянные/повреждённые
файлы, symlink, traversal, лишние сертификаты, подмена счётчиков. CI также
проверяет синтаксис shell scripts. Production-данные этим тестам не нужны.

`scripts/check-backup.sh` после сборки образа проверяет полный цикл настоящим
Restic в одноразовом контейнере с `--network none`, без host/production mounts:
init, backup, retention, current/previous, weekly check, monthly read/restore,
export и отказ при неверном ключе, пропавшем фото, чужом snapshot и занятом
lock. Данные и тестовый зашифрованный репозиторий находятся только в tmpfs.
На 04.10 эти проверки пройдены; web Compose-конфигурация осталась прежней,
реестр стеков (`check.sh --fast`) и systemd units прошли статическую проверку.
