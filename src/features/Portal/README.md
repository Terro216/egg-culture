# Единый аккаунт игр

`/{ru,en}/profile/` — вход, восстановление, настройки видимости, результаты
пяти общих игр и достижения. `/{lang}/adepts/{publicId}/` — публичная
страница; закрытый или неизвестный профиль возвращает 404. Страницы RU/EN
не индексируются; публичные страницы и ответы API не кэшируются. Владелец может делиться обычной публичной
ссылкой: её идентификатор не является ключом доступа или идентификатором сессии.

## Идентичность и данные

- Переиспользуются проверенные логин/пароль, scrypt, восстановление,
  HttpOnly/Secure cookies, ограничения входа и SQLite «Пути формы».
- `/api/portal-account` — алиас действующего `/api/egg-road-account`.
  Старые клиенты и аккаунты продолжают работать без новой регистрации.
- Добавочные таблицы в существующей `records.sqlite`: настройки,
  лучшие результаты, достижения, принятые UUID забегов и маркеры миграций. Старые записи,
  пароли, восстановления и сессии не преобразуются и не удаляются.
- По выбору владельца портала новые регистрации публичные сразу. Текст
  регистрации предупреждает об этом. По отдельному запросу 2026-09-20
  существующие зарегистрированные профили однократно становятся публичными
  при миграции `public-profiles-fry3-20260920`. Публичные ID и знаки сохраняются;
  аккаунты без профиля получают его. Гости не публикуются. Последующее ручное
  скрытие профиля сохраняется при перезапусках; миграция больше не повторяется.
- Публичный ответ содержит только случайный publicId, имя, знак,
  результаты, номер текущего сезона Жарки и идентификаторы достижений. Не содержит player/session/guest,
  cookies, паролей, кодов восстановления, IP, истории входов и предсказаний.
- Скрытие профиля также скрывает ссылки на него в таблицах дорог, но не
  удаляет сами ранее отдельно опубликованные дорожные рекорды.
- Игры страницы Фонина не подключены: её подарки и результаты не попадают
  в общие профили.

## Запись результатов

`POST /api/portal-profile` требует действующую сессию, точный Origin,
JSON, ограниченный размер тела и совпадение имени начавшего забег аккаунта.
Все поля проходят валидацию; большие числа передаются десятичными строками.
Сервер выводит достижения из метрик, а не принимает произвольный список.
Это личная статистика браузерных игр, не защищённый от читов рейтинг.

UUID фиксируется при старте забега. Один UUID засчитывается один раз,
включая повтор после таймаута с неизвестным исходом. Клиентская очередь
привязана к аккаунту; каждый забег занимает отдельный ключ, чтобы разные
вкладки не перетирали общий массив. При смене аккаунта чужая очередь не
отправляется, поздний ответ не меняет нового пользователя. При запрете
localStorage очередь живёт только до закрытия вкладки; гостевые результаты
остаются локальными. Импорт старых локальных рекордов в чужой аккаунт
автоматически не выполняется. Архив первого сезона Жарки остаётся локальным.

Третий сезон Жарки начинает новый зачёт. В API используется `game: fry,
season: 3`, в SQLite — отдельный ключ `fry3`, в браузере — `egg_fry_v3`.
Старые вкладки/очереди без season считаются вторым сезоном и пишут в прежний
ключ `fry`; эти значения не включаются в текущий профиль. UUID остаются
общими, повторная отправка не создаёт второй результат. Ответы старого
сервера без `frySeason: 3` не импортируют баллы в новый локальный зачёт.
Другие игры, пароли, сессии и накопленные достижения не сбрасываются.

«Халазы судьбы» используют `game: untangle` и прежнюю очередь с UUID.
Поле `untangle` содержит канонический seed NEST1/NEST2/NEST3/KNOT1/KNOT2, уровень 1–24, режим
`campaign | daily | free`, день `YYYY-MM-DD` только для ежедневной кладки,
число ходов и подсказок, окончательные координаты узлов. `score` и `peak`
равны строке уровня, `seconds` содержит время активной игры, остальные
счётчики равны нулю. Сервер заново генерирует граф, проверяет координаты,
отсутствие пересечений и совпадение с кампанией или кладкой указанного дня.
NEST2 — Путь адепта, KNOT1 — режим перестановок; NEST3 и KNOT2 заменяют
только первые три ступени соответствующей кампании учебными задачами.
Прежние коды воспроизводят прежние задачи. Для перестановок сервер дополнительно
проверяет, что результат является точной перестановкой исходных гнёзд,
каждое гнездо занято ровно один раз. Режим определяется версией seed,
доверять отдельному клиентскому флагу не требуется. Прежние NEST1-коды,
кампании, ежедневные кладки и отложенные результаты продолжают приниматься.
День меняется в 00:00 по Москве; предыдущие дни принимаются для отложенной
синхронизации, будущие — нет. Ходы, подсказки и время остаются метриками
клиента; проверка решения не является защитой от подделки этих метрик.

Добавочная таблица `untangle_puzzles` хранит отдельный результат каждого
seed внутри аккаунта: независимые минимумы ходов, времени и подсказок,
число решений и канонический режим. Повторы одного seed не увеличивают
число разных кладок; один UUID не увеличивает и число попыток. Свободное
решение можно позднее зачесть в соответствующей кампании или кладке дня.
Обновление записи, UUID, статистики и достижений выполняется одной
транзакцией. Все ступени каждой версии и все дни остаются в SQLite после
перезапуска. Маркер `campaignVersion: 2` отличает новый ответ от запоздалого
ответа прежнего сервера. Личный `campaign` объединяет ступени NEST2 и NEST3,
`hardCampaign` — KNOT1 и KNOT2, `legacyCampaign` — NEST1. Пройденные прежде
первые три ступени остаются зачтёнными; две версии одной ступени не удваивают
её зачёт, а личные рекорды каждого seed сохраняются отдельно. Достижение
обычной кампании требует все 24 ступени текущей кампании либо все 24 NEST1:
смешать неполные старую и текущую кампании нельзя.

Личный ответ `untangle` возвращает завершённые ступени, агрегаты и до 256
записей (все ступени кампании сохраняются в этом окне). Публичный ответ
содержит только число кладок, высший уровень, число ступеней обоих режимов,
число прежних ступеней, кладок дня
и текущую серию; seed, даты и личные лучшие ходы/время остаются приватными.
Девять достижений выдаются из проверенных решений и накопленного прогресса.
Серия сохраняется до окончания следующего московского дня; историческая
серия из семи дней засчитывается и после отложенной отправки.

Завершённую гостевую кладку можно явно сохранить после входа через
`importGuestPortalResult(ticket, values, expectedOwner)`. Вызов разрешён
только для `game: untangle`, гостевого ticket и явно выбранного текущего
аккаунта. Функция сохраняет исходный UUID, проверяет идентичность до и
после ожидания загрузки профиля и помещает результат в прежнюю очередь
с `guestImport: true`. Автоматического импорта при входе нет. Таблица
`untangle_guest_claims` транзакционно связывает UUID гостевой попытки с одним
аккаунтом; повторы для того же владельца идемпотентны. Другой аккаунт
получает `guest_result_claimed` (409), без частичной записи. Клиент снимает
такую окончательно отклонённую попытку с очереди и публикует `resultError`,
чтобы остальные результаты могли синхронизироваться. Сетевая ошибка
по-прежнему сохраняет попытку для повторной отправки.
При гостевом переносе достижения и уведомления появляются только после
подтверждения сервера; постановка в очередь сама по себе их не выдаёт.
Скрыть гостевой результат разрешается только после устойчивой записи его
UUID и доказательства в очередь аккаунта. Если большая запись упёрлась
в квоту, перенос возвращает отказ: малая отметка «уже перенесено» не может
скрыть исходный результат. Повторная попытка заново сохраняет ту же запись.

## Проверка и выпуск

`tests/portal-profile.test.mjs`, `tests/portal-client.test.mjs`,
`tests/egg-untangle-profile.test.mjs` проверяют
совместимость с прежними аккаунтами, однократную публичность миграции, публичные новые
аккаунты, CSRF, точные числа, идемпотентность, отзыв публичности, очереди,
гонки ответов, изоляцию сезонов и пользовательских данных, проверку графа,
отклонение чужих seed/дат, сохранность разных кладок, дневные серии и
ограниченный размер личного ответа. Браузерный сценарий
`scripts/verify-portal.mjs` разрешён только для изолированного loopback preview
с собственным временным каталогом SQLite, никогда для production.

Для выпуска требуется отдельное подтверждение. Сохранить предыдущий образ
и резервную копию `records.sqlite`, затем пересоздать только `web`, сохранив
имеющийся том. Дополнительные таблицы совместимы с откатом на предыдущий
образ. Откат образа не отменяет разрешённое изменение публичности в базе;
для отката видимости требуется отдельное решение, данные сохраняются.
